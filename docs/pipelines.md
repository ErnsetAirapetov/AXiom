# Пайплайны: как система работает

Логика работы программы: что происходит по шагам при запросе пользователя и
при наполнении базы. Технологии — в `stack.md`, обоснование схемы поиска —
в `retrieval-design.md`.

Стадия изысканий: пайплайны описаны на уровне шагов и ответственности, без
привязки к реализации. Спорные места помечены.

## Пайплайн пользователя

```
1. ВОПРОС
2. УТОЧНЕНИЕ КОНТЕКСТА
3. ПОИСК
4. ПРОВЕРКА АКТУАЛЬНОСТИ
5. СБОРКА ОТВЕТА
6. ОБРАТНАЯ СВЯЗЬ
```

**1. Вопрос.** Проектировщик пишет на естественном языке. Опционально —
контекст проекта: категория дороги, регион, стадия проектирования, тип
конструкции.

**2. Уточнение контекста.** Если от недостающего параметра зависит ответ,
система спрашивает. Категория дороги меняет почти всё; отвечать без неё —
гарантированно ошибиться. Правило, ограничивающее навязчивость: спрашивать
только то, что реально меняет ответ, а не всё, что можно спросить.

**3. Поиск.** Два раздельных запроса — по нормативному индексу и по
экспертному. Итеративно: система вправе сделать несколько обращений к
индексу, уточняя запрос по промежуточному результату. Обращение к индексу
стоит копейки, поэтому итеративность здесь дешёвая (см.
`retrieval-design.md`).

**4. Проверка актуальности.** Каждый найденный пункт сверяется со статусом
редакции. Недействующее либо отсекается, либо помечается явно — но никогда
не подаётся молча как действующее.

**5. Сборка ответа.** Сводка + дословные цитаты + ссылка на
документ / пункт / редакцию. Нормативный и экспертный блоки разделены
визуально. Если источники расходятся — показать оба, не выбирать за
проектировщика.

**6. Обратная связь.** «Полезно / мимо / здесь ошибка». Это не украшение
интерфейса: это основной источник данных для улучшения поиска и материал
для набора эталонов. Запрос, ответ и оценка сохраняются в историю — через
полгода она сама по себе база знаний о том, что спрашивают чаще всего.

**Ветка «ничего не нашли»** — отдельная, а не «модель что-нибудь напишет».
Механика в разделе «Качество ответа» ниже.

## Качество ответа: четыре уровня защиты

Требование «ни одного утверждения без ссылки» не выполняется одним
промптом. Оно собирается слоями, каждый со своей ценой.

**Уровень 1 — порог релевантности (программный).**
Топ-результат ниже порога → модель не вызывается вообще, система отвечает
«не нашлось». Дёшево и надёжно, но порог как инструмент грубый.

**Уровень 2 — проверка релевантности найденного (дешёвая модель).**
Короткий вызов: «Содержат ли эти фрагменты ответ на этот вопрос? да /
частично / нет». Стоит доли цента, закрывает главную дыру порогового
подхода — случай «поиск что-то нашёл, но не то». При ответе «нет» —
переформулировать запрос и искать снова либо честно сказать, что не
нашлось.

**Уровень 3 — сборка с явными инструкциями (сильная модель).**
Модель обязана отдельно отмечать: расходятся ли источники, хватает ли
данных для полного ответа, какие условия применимости у каждого пункта.

**Уровень 4 — проверка после генерации (выборочно).**
Отдельный вызов сверяет каждое утверждение готового ответа с цитатами:
подкреплено или додумано. Дорого, поэтому не на каждый запрос — на первых
месяцах на всех (это данные о качестве), затем на выборке и на явно
сложных запросах.

Ориентир, почему это не паранойя: в исследованиях юридического RAG доля
галлюцинированных ссылок держится на уровне **13–21% даже в системах с
retrieval**. Без слоя проверки система выдаст свою цифру в этом же
диапазоне, и никто об этом не узнает.

### Противоречие или разная применимость

Модель путает две разные ситуации:

- **реальное противоречие** — два действующих пункта требуют разного в
  одних и тех же условиях;
- **разная область применения** — два пункта дают разные числа, потому
  что относятся к разным категориям дорог, регионам или конструкциям.

Второе противоречием не является, но без метаданных применимости
неотличимо от первого. Практический вывод: **область применения должна быть
явным полем у пункта**, а не подразумеваться из текста.

### Абсурдность ответа

Модель ловит абсурд неплохо, но только имея контекст проекта. «Радиус
15 метров» абсурден для категории IА и нормален для съезда — чтобы
отличить, надо знать, о чём речь. Это дополнительный довод за шаг
уточнения контекста.

## Пайплайн наполнения: нормативы

```
1. ПРИЁМКА (карточка документа)
2. ИЗВЛЕЧЕНИЕ ТЕКСТА И СТРУКТУРЫ
3. РАЗБИЕНИЕ НА ПУНКТЫ
4. ВЫБОРОЧНАЯ ПРОВЕРКА ЧЕЛОВЕКОМ
5. ИНДЕКСАЦИЯ
6. ПУБЛИКАЦИЯ
```

**1. Приёмка.** Файл + карточка: обозначение, наименование, издатель, дата
введения, статус (действует / отменён / заменён), что заменяет, чем
заменён, область применения. Карточка заполняется **до** загрузки текста;
документ без карточки в базу не попадает.

**2. Извлечение текста и структуры.** Парсинг: текст, заголовки разделов,
нумерация пунктов, таблицы, приложения. Самое трудное место всего проекта —
нормативы это PDF с таблицами, формулами и графикой.

**3. Разбиение на пункты.** По структуре документа, не по количеству
символов. Каждый пункт получает устойчивый идентификатор:
документ + редакция + номер пункта. Единица индексации обязана совпадать с
единицей цитирования — иначе ссылку неоткуда взять.

**4. Выборочная проверка человеком.** На первых 10–20 документах —
сплошная. Дальше — выборка. Без этого не выяснится, что парсер молча теряет
таблицы.

**5. Индексация.** См. `retrieval-design.md` — что именно индексируется и
в каком виде.

**6. Публикация.** Документ становится видимым для поиска.

**Новая редакция — не перезапись.** Новая версия + связь «заменяет».
Старая остаётся доступной и помечается недействующей: проектировщику
иногда нужно знать, что было раньше — проект мог разрабатываться по
прошлой редакции.

## Пайплайн наполнения: экспертный слой

Главный риск здесь не технический, а человеческий: **если заполнение стоит
эксперту больше двух минут, слой останется пустым.**

Два разных потока:

- **замечание экспертизы + ответ на него** — приходит пачкой, разбирается
  постфактум: загрузка документа с замечаниями, разбор на отдельные записи,
  эксперт правит и подтверждает;
- **заметка эксперта** — «я только что понял, надо записать»: форма из трёх
  полей, не больше.

**Обязательные поля:**

- суть — что именно является нормой практики;
- границы применимости — регион / тип конструкции / условия. Без этого
  запись вредна: её применят не там;
- автор и дата.

**Привязка к нормативу** — опционально: к какому пункту относится, или
«нормативом не покрыто».

**Модерация.** Кто-то подтверждает, что это норма практики, а не частное
мнение одного человека. Без модерации слой быстро заполнится
противоречиями.

**Индексация — в отдельный индекс.** Не в общий пул с нормативами: иначе
слои смешаются на уровне поиска, и разделение в интерфейсе уже ничего не
спасёт.
