# Технологический стек и масштабирование

Что берём на MVP, почему именно это, и как оно растёт от отдела до
нескольких компаний. Обоснование схемы поиска — в `retrieval-design.md`,
шаги работы — в `pipelines.md`.

**Стадия изысканий.** Ничего из перечисленного не выбрано окончательно —
это рабочая гипотеза для первого прогона, а не решение. Принятые решения
фиксируются в `decisions.md`.

## Принцип отбора

Легко начать — легко масштабировать. Из двух вариантов выбирается тот, где
меньше движущихся частей, даже ценой запаса по производительности. Стартуем
на отделе, поэтому нагрузка на старте — десятки пользователей, а не тысячи.

## Минимальный стек MVP

| Слой | Гипотеза | Когда пересматривать |
|---|---|---|
| Хранилище | **PostgreSQL** — карточки документов, пункты, версии, экспертные записи, история запросов | Долго не понадобится |
| Лексический поиск | **Postgres full-text search** с русской морфологией | — |
| Векторный поиск | **pgvector** в той же базе | Когда объём перестанет помещаться → выделенная векторная БД |
| Эмбеддинги | Многоязычная модель **локально** | — |
| Файлы | Папка на диске или S3-совместимое хранилище | — |
| Модель | **Claude через API** | — |
| Логика | **Python** + Anthropic SDK, без фреймворка | Когда пайплайн стабилизируется |
| Интерфейс | **Streamlit** | Когда отдел скажет «неудобно» |
| Парсинг PDF | **Docling** (кандидат) | По результатам первых документов |

Одна база, один процесс, один сервер. Разворачивается на чём угодно,
включая ноутбук.

**Почему одна база для всего.** Метаданные, полнотекстовый и векторный
поиск в одном Postgres означают, что фильтр по метаданным и поиск по смыслу
делаются одним запросом. Разнеси их по трём системам — и придётся
согласовывать состояние между ними на каждой индексации.

**Почему эмбеддинги локально.** Они гоняются миллионы раз при индексации;
отправлять каждый фрагмент в облако дорого и бессмысленно. Локальная модель
делает векторизацию практически бесплатной — платим только за вычисления.

**Почему без фреймворка на старте.** LlamaIndex и Haystack прячут именно ту
логику, которую сейчас надо понять и отладить: как ищется, что попало в
контекст, почему модель ответила именно так. Пока пайплайн не устоялся,
фреймворк мешает. Когда устоится — переезд занимает пару дней.

## Модель

**Разделение по ролям** — не одна модель на всё:

| Задача | Тир | Почему |
|---|---|---|
| Сборка ответа | Сильная | Нужна дисциплина следования инструкциям: не выдумывать, цитировать дословно, помечать источник |
| Уточняющие вопросы, переписывание запроса | Дешёвая | Простая задача, высокая частота |
| Проверка релевантности найденного | Дешёвая | Короткий вход, короткий выход |
| Обогащение пунктов и генерация вопросов при индексации | Дешёвая | Разово на документ, но объём большой |

Обрати внимание: на сборке ответа от модели требуется **дисциплина
следования инструкциям**, а не знание дорожного проектирования. Это меняет
критерий выбора модели.

### Стоимость и подписка

**Подписка Claude и доступ к API — разные вещи.** Подписка даёт работу в
чате и в Claude Code, но не даёт квоту для программных вызовов из
приложения. Для платформы нужен отдельный API-ключ, тарифицируемый по
токенам.

Порядок цен на 2026-08-04 (вход / выход за млн токенов): Claude Opus 5 —
$5 / $25, Claude Sonnet 5 — $3 / $15. При двадцати пользователях в отделе
счёт измеряется десятками долларов в месяц.

**Кэширование промптов заложить сразу** — системная инструкция будет
большой и одинаковой между запросами, экономия на повторяющейся части
достигает 90%.

## Оркестрация: где она понадобится

В **пайплайне запроса** оркестратор не нужен: цепочка короткая, падение не
критично — пользователь переспросит.

В **пайплайне наполнения** нужен. Разбор PDF → извлечение структуры →
разбиение на пункты → обогащение через модель → генерация вопросов →
векторизация: это часы работы на сотнях документов с вызовами модели
внутри. Падение на трёхсотом документе не должно означать перезапуск с
нуля. Кандидат — **DBOS** (есть опыт у владельца на соседнем проекте,
хранит состояние в Postgres, что совпадает с нашим хранилищем).

Заводить не на старте — когда дойдём до массовой индексации.

## Путь масштабирования

Отдел → компания → несколько компаний. Одно архитектурное решение,
принятое сейчас, определяет весь путь:

```
ОБЩИЙ СЛОЙ                        ПРИВАТНЫЙ СЛОЙ
(нормативы — одинаковы            (экспертиза — своя
 для всех)                         у каждой компании)
     │                                   │
     └──────────────┬────────────────────┘
                    │
              поиск идёт по обоим,
              приватный виден только своим
```

Заложить это разделение с первого дня — и путь до нескольких компаний
становится вопросом конфигурации. Не заложить — на третьем шаге переписывать
придётся всё.

Практически: **у каждой записи экспертного слоя с самого начала есть поле
владельца**, даже когда владелец всегда один и тот же. Стоит это ноль,
экономит месяцы.

### Что меняется на каждом шаге

| Шаг | Что упирается первым | Ответ |
|---|---|---|
| Отдел (~20 чел.) | Ничего | Стек выше |
| Компания (сотни) | Латентность поиска, конкурентные запросы | Кэш частых запросов; при необходимости — выделенная векторная БД |
| Несколько компаний | Изоляция данных, разграничение доступа | Разделение слоёв, заложенное на первом шаге; плюс аутентификация и аудит |

## Открытые вопросы стека

- где живут данные — закрытый контур или облако (влияет на выбор модели
  для сборки ответа);
- насколько локальная модель проигрывает облачной на нашем наборе
  эталонов — решать по цифрам, а не по идеологии;
- какой парсер PDF выдерживает реальные нормативы с таблицами и
  приложениями.
